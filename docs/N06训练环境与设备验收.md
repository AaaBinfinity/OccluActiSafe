# N06 训练环境与设备验收

本节点建立设备级训练能力证据，不训练GRU、HiVT或RC-STGT，不读取TFD标签。N05已获用户验收；N06当前结果与用户验收状态统一见[节点计划](项目节点实施与验收计划.md#n06-实际训练环境与gpu资源验收)。数据坐标一致性与稀少类别限制保持未解决，设备通过不能推出数据或课题模型训练就绪。

## 首次准备与日常运行

项目仍使用仓库`.venv`与Python3.11。轻量依赖保留，新增非默认`training`依赖组，仅包含当前需要的PyTorch及其传递依赖，不安装torchvision、检测器、CARLA或权重。Windows/Linux的Torch来源绑定官方CUDA12.8专用索引；其他平台的解析不作为本机验证。版本选择参考[官方安装说明](https://pytorch.org/get-started/locally/)、[官方CUDA12.8构建索引](https://download.pytorch.org/whl/cu128/torch/)，实际构建与SHA-256以`uv.lock`及本机证据为准，不将网页安装选择器的缓存版本号当作本机安装结果。

首次准备：`uv sync --locked --group training --python 3.11`。本机为避免安装包缓存写入普通Git，实际另传`--cache-dir H:/OccluActiSafeDataset/artifacts/uv_cache --link-mode copy`；缓存与环境分盘，`.venv`仍在本机仓库。运行时不安装、不下载、不自动找盘；若后续只执行`uv sync --locked`可能移除未选择的训练组，训练电脑重建时应明确传`--group training`。CARLA桥接兼容性留给N12，不由本节点声称已兼容。

日常在IDE选择仓库`.venv/Scripts/python.exe`，直接运行`scripts/smoke_check.py`。默认配置`configs/runtime/n06.yaml`，脚本`OVERRIDES={}`，可选CLI覆盖`--config/--device/--seed/--allocator-limit-mib/--output-root`；路径从项目根解析，不依赖cwd，import不执行任务。`scripts/check_environment.py`默认继续只检查轻量安装、不导入Torch或初始化CUDA；显式`--gpu`才查询CUDA设备与构建信息，完整前后向仍须运行smoke。

## 输入、步骤、输出和测试

`common/device.py`提供惰性`import_torch()`、`select_device()`、`seed_everything()`、`inventory()`。设备必须明确为`cuda:N`或显式CPU诊断；禁止auto及隐式CPU回退。缺依赖、CPU构建、CUDA不可用、非法设备、运行中无兼容kernel均须明确失败。版本兼容性以实际内核运算验证，不能只凭`is_available()`或设备名。

`common/device_smoke.py:run(config)`创建唯一run及配置快照。默认seed17、float32、512×512随机矩阵乘法、64×16输入、16→128→2的Linear/Tanh小网络、SGD(lr=.01)更新5步。这些是明确构造的设备机制夹具，不伪装为真实交通样本。逐步检查loss和所有梯度有限、张量与参数在指定设备、参数变化；矩阵结果单元素另以点积复核。先同步再计时，结束再次同步；报告矩阵/优化墙钟秒数、GPU当前空闲/总字节、进程分配器峰值allocated/reserved字节、Torch/CUDA/cuDNN/编译架构及nvidia-smi驱动/UUID清单。

同一run重设Python、NumPy和Torch种子执行两次完整诊断，要求loss、梯度范数、矩阵/输出/参数字节哈希一致。使用`CUBLAS_WORKSPACE_CONFIG=:4096:8`（兼容已有`:16:8`）、确定性算法报错模式、cuDNN benchmark=False/deterministic=True，禁用TF32；不兼容的外部workspace配置明确拒绝。范围只覆盖本机构建下本夹具的float32矩阵、Linear/Tanh/SGD；不保证跨设备、版本、全部算子或后续GRU/注意力确定性，相关节点须另测。依据见[PyTorch 2.11可复现性文档](https://docs.pytorch.org/docs/2.11/notes/randomness.html)。

每run保存manifest、task_config、device_inventory、device_smoke、training_budget、evidence_index及status。失败保留failed状态、类型、原因与已生成产物，不写成功结果；CPU显式标`cpu_diagnostic`、显存字段null，不计GPU验收。大文件、测试日志与运行证据全部在H盘，普通Git只保留实现、配置、测试和Markdown。

测试分为：`python -B -m unittest discover -s tests/unit -v`执行新增6项拒绝/配置机制与既有回归；`python -B -m unittest discover -s tests/gpu -v`必须在真实GPU执行4项设备测试，缺硬件/依赖会失败，不能skip。GPU测试覆盖17/29/43三个种子各两次完整前后向、三个cwd无必填CLI且跨进程输出哈希一致、无效cuda:999拒绝、实际分配器受控OOM及显式CPU诊断。日志中的OOM为将该子进程CUDA分配器限制为1MiB后触发的真实OutOfMemoryError，验证错误处理，不能称为耗尽整张显卡或测得可训练模型最大规模；不主动耗尽系统或其他应用显存。模拟CPU构建/缺Torch仅证明拒绝分支，不冒充安装了另一构建实测。

## 后续单次训练资源预算

N06在`configs/runtime/n06.yaml:training_budget`冻结本机保守上限：单次7200秒、最多20000次优化更新、最多60epoch，最早触及者停止；GPU分配器最多12288MiB、主进程工作集目标上限8192MiB、DataLoader workers=0，比较种子固定[17,29,43]。12GiB为分配器上限，不含驱动、CUDA context或其他进程显存，不能保证一定分配成功。当前设备smoke最低空闲显存512MiB，真实任务还须在实际启动时按模型核查需求。

这些是N06职责内为16GB主机设定的资源保护预算，不是最优训练超参，也不证明小网络测试已覆盖12GiB容量或长训练稳定性。技术路线中的80epoch等起步示例仍属设计，实际本机任务须服从本预算；若后续任务需扩预算，应先说明原因与影响并确认。N06只在smoke进程施加CUDA分配器上限，不提前实现N07训练器；时间/步数/epoch、主机内存及DataLoader限制必须由后续获授权的训练入口实际执行并记录，尚未声称这些未来入口已存在或已测试。显存不足不得换CPU冒充，缩批等运行选择须重新登记，完整失败保留。
