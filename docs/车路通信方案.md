# 路侧端与车载端通信方案

对应课题：基于 Transformer 的超视野车路协同主动避撞方案研究  
版本：V1.2\
更新日期：2026年10月26日  
状态：拟实施设计。尚未实现跨进程网络通信、部署 RSU/OBU 或完成通信与避撞联合实验。

本文件解释真实部署所需链路，并规定本毕设的软件通信原型。算法与控制设计见 [详细技术路线](详细技术路线.md) 第7、21.5和22章。摄像头提供观测，路侧边缘计算生成目标与预测，车辆接收后复核风险并执行制动或转向。

## 1 真实部署怎样连接

推荐的硬件链路为：

路侧摄像头 → 以太网/光纤 → 路侧边缘计算设备 → 路侧通信单元 RSU ⇄ 无线链路 ⇄ 车载通信单元 OBU → 车载计算与控制器 → 制动/转向执行器。

车载状态和本地目标沿相反方向上传。RSU（Road Side Unit）负责路侧无线收发，OBU（On Board Unit）负责车上无线收发；它们可以与计算设备集成在同一机箱，也可以独立部署。车辆内部由 OBU 通过车型提供的车载以太网/CAN及网关接口接入计算与控制系统，具体取决于车辆架构。这里的车载计算与控制器指负责辅助驾驶的计算单元和控制器。

路侧原始视频主要在本地有线链路传输。V2X链路承载位置、速度、轨迹模式、观测时间和质量等结构化结果。多辆车可共享路侧观测；每辆车仍根据自己的位置、速度、侧向空间和车辆约束分别做决定。

### 1.1 无线链路的两种选择

| 路径 | 数据经过哪里 | 本课题中的用途 |
| --- | --- | --- |
| C-V2X PC5 直连 | 路侧 RSU 与车载 OBU 直接交换消息 | 推荐作为局部路口协同的目标部署架构；选择兼容的无线制式与设备协议栈 |
| 4G/5G Uu 网络路径 | 车辆蜂窝终端 → 基站/移动网络 → 边缘应用服务器，路侧设备接入该服务器 | 可作为另一种部署路径；需要测量整条链路的时延和可用性 |

C-V2X包含直接通信PC5与移动网络通信Uu。PC5可采用不依赖蜂窝网络参与的直接通信方式；Uu经运营商网络。二者的关系与定义依据[5GAA官方说明](https://5gaa.org/c-v2x-explained/)。本课题推荐PC5目标架构属于设计选择，不代表已完成设备测试或优于所有网络方案。

实际PC5对接通过选定RSU/OBU厂商的SDK、服务标识和消息接口完成。原型里的IP地址、UDP端口属于软件传输配置；它们不能直接证明已实现PC5无线协议。发送频率、覆盖距离和低时延均不能仅凭“使用5G”推定。

算法核心与最终车端决策已按[算法成品与盲区鬼探头方案](算法成品与盲区鬼探头方案.md)明确。路侧消息是算法输入，界面订阅输出；同机仿真不改变车端权限。目标协议增加车辆/行人/骑行者类别和尺寸质量；未知遮挡区域使用独立区域字段，不能伪装成已检测目标。

## 2 双向到底传什么

| 方向 | 逻辑消息 | 主要内容 | 原型起步频率 |
| --- | --- | --- | --- |
| 车 → 路（V2I） | ObservationMessage | 本车位置、速度、航向、尺寸；车载可观测目标及其质量与采集时间 | 10 Hz |
| 路 → 车（I2V） | PredictionMessage | 统一目标ID、最新状态、尺寸/质量、未来多模式轨迹、模式权重、地图与时间信息 | 10 Hz，结果实际可用后发送 |
| 车 ↔ 路侧协调器 | IntentMessage，扩展项 | 候选意图、proposal_id、有效期、确认/拒绝与执行状态 | 事件触发，并按协议续期 |
| 双向 | HealthMessage | 设备会话、健康状态和最近处理序号 | 低频，频率待联调冻结 |

10 Hz是本课题与轨迹采样、规划周期对齐的初始配置，不是V2X标准规定。车端控制以20 Hz执行，不需要等待每次路侧更新。上传车载检测结果不是所有应用的必要条件，但本课题研究双来源融合，需要实现该方向。路侧只接收已经到达的上传消息，不能跨过V2I时延直接读取车端缓存。

消息里的本地目标ID必须包含来源和会话命名空间，例如“vehicle_A/session_01/camera_front/track_7”。跨视角关联由位置、运动和质量完成，不能借用CARLA真值ID解决关联。

## 3 消息协议怎样定义

以下为研究内部协议，后续实际部署需按设备SDK和目标应用标准另行映射。先用Python数据类/Pydantic定义结构与校验；JSON用于调试，二进制传输版本可选Protobuf并冻结schema。

### 3.1 公共头与接收端元数据

| 字段 | 语义 |
| --- | --- |
| schema_version、message_type | 协议版本和消息类型；版本不兼容时拒绝 |
| source_id、session_id、sequence | 来源、进程/设备会话、会话内递增序号；重启后建立新会话 |
| recipient_id或service_area_id | 指定接收车或服务区域；避免把其他区域结果误用 |
| map_id、map_version、coordinate_frame_id | 地图与坐标系标识；位置m、速度m/s、航向rad，轴方向和参考点单独声明 |
| frame_id | 采集/仿真帧序号，与TickEvent帧号语义一致；不充当坐标系名称 |
| generated_time、transmitted_time | 消息生成时间和实际发送时间，处于同一声明的时钟域 |
| valid_until | 允许采用该消息的最晚时刻，属于新鲜度/有效期约束 |
| arrival_time、usable_time | 接收端或仿真调度器记录的到达、完成接收处理并可被消费的时刻 |

arrival_time不能由发送端伪装成测得的接收时间。原技术路线表中的消息对象包含接收端元数据，不意味着所有字段都在线上传输。分片重组、解码和校验未完成前，usable_time尚未达到，控制器不得读取半条消息。

### 3.2 观测消息

每个目标携带observation_time、last_seen_time、位置/速度/航向、车长宽、状态参考点、source、质量/协方差及缺失掩码。若状态已被因果外推，另存state_time；原始采集时刻不变。上传本车状态与上传周边目标分别标记，防止本车被重复当作障碍物。

消息只需上传增量可用观测，路侧维护约2秒历史缓存，不必每0.1秒重复上传完整历史。首次建立会话或恢复连接时可请求有时间标记的历史补充；补充历史仍按真实到达时间使用。

### 3.3 预测消息

每个目标携带模式轨迹[K,T,2]、权重[K]、有效时间掩码、最新状态与几何尺寸，以及来源观测年龄/质量。本课题主配置K=6、T=40、间隔0.1秒，输出为统一地图坐标。

全局字段至少包括model_hash、anchor_time、input_cutoff、completed_time、future_times、future_end和valid_until。future_times[j]=anchor_time+(j+1)×0.1；anchor处的状态单独随消息给出，供第一个预测采样点之前的对齐使用。future_end表示预测终点；valid_until表示消息最晚采用时间，二者不能混用。字段不一致时拒绝消息。

权重需有限、非负且对有效模式归一；有效轨迹不能含NaN/Inf。每目标的有效终点可能比全局future_end更早，覆盖检查按相关目标的实际有效部分进行。路侧可附风险提示，但最终风险由车端针对当前候选动作、道路条件和共同预测窗口计算。

## 4 毕设如何一步步实现

### 4.1 第一阶段：可重复的通信仿真

在同一程序中先建立两个独立SimChannel：V2I和I2V。按技术路线21.5节的heapq设计，以(arrival_time,counter,packet)调度，N08同时实现第6节的容量服务时间和有界排队，不依赖UDP。N11先接解析时钟，N12后才接CARLA唯一tick调度器；消息只有到usable_time才能消费，不要求N08先有CARLA。

基本步骤：车端采集/感知完成 → V2I排队与传输 → 路侧关联/预测完成 → I2V排队与传输 → 车端解码和时效检查 → 风险与可行性复核 → MPC/回退执行。每个环节都保留独立时间戳和延迟。

延迟先用固定值联调，再加入有界抖动、Bernoulli丢包、预生成的突发断联区间和乱序。随机扰动绑定方向、source/session/sequence/chunk身份，或预生成通信扰动表，保证不同策略受到可比较的通信条件。避免因策略分支的抽样次数不同而破坏配对实验。

本阶段验证的是应用层在通信扰动下的行为。只用固定延迟和丢包率，尚不足以建立真实PC5的射频、资源调度与拥塞模型。

### 4.2 第二阶段：分进程与跨机器原型

路侧服务和车端服务分别运行，保持同一消息接口。可以在本机用进程间队列联调，再通过Python socket实现UDP收发；socket提供网络接口的依据见[Python官方文档](https://docs.python.org/3/library/socket.html)。冻结IP/端口、node_id、服务区域与协议版本，先用回环网络，再在局域网两台设备之间验证。

实时观测/预测使用UDP时，应用实现序号去重、截止时间、消息大小限制、分片重组和限速。UDP自身不提供可靠交付或拥塞控制，设计依据见[RFC 8085](https://www.rfc-editor.org/rfc/rfc8085.html)。旧预测超过截止时间后丢弃，优先消费新结果；不能在接收线程中无限积压。最新待执行任务缓存可限定为1，但历史缓存与危险目标记忆另行保留。

配置和日志可使用独立TCP/HTTP通道；该通道的重试不能阻塞实时控制循环。意图协同需要应用层proposal/确认/超时状态机，即使底层可靠传输也不能假设另一辆车已按计划执行。

实测跨进程计算与网络耗时应单独记录。受控仿真阶段统一由调度器提供simulation_time；接收服务输出的结果到达后，还需等待simulated_usable_time。不得混用系统墙钟与仿真时钟，也不得把同一段实测网络耗时和注入耗时重复累计。

### 4.3 第三阶段：有条件时接真实设备

选用兼容的RSU/OBU，替换传输适配层，保持上层消息、时间和回退接口。按设备能力适配标准消息、证书和防重放机制，实测端到端时延、吞吐与丢包。当前没有实车和通信设备，毕业设计核心验收以软件原型和CARLA闭环为准；论文只能报告实际完成的通信层级。

## 5 收到预测之后怎样对齐

假设路侧anchor_time=12.0s，预测至16.0s；车端在12.2s收到，检查、决策与执行延迟后预计12.25s开始执行。车端3秒规划的对比窗口为12.25～15.25s，按这段绝对时间读取路侧轨迹。不能将12.1s的预测点改成“收到后0.1秒”的位置。

每次决策依次检查：

1. 来源/会话、协议、地图/坐标、数据有限性、模式权重及顺序是否有效。
2. 消息是否已到usable_time；当前时刻是否未超过valid_until。
3. 每个相关目标的原始观测年龄、预测锚点年龄是否在冻结配置允许范围内。
4. 有效未来是否覆盖预计执行起点+3秒，并预留时钟误差裕量。
5. 本车最新可观测目标与路侧预测是否明显冲突，侧向通道是否可用。

例如同一消息到12.9s才收到，预计13.1s执行，3秒规划需要覆盖至16.1s；即便消息TTL尚未到期，预测终点16.0s也不足。coverage_complete=false时进入补充预测/谨慎策略，不能仅因短窗口风险低而正常通过。

4秒路侧预测与3秒规划之差，只提供锚点之后约1秒的时间裕量；还需分配下发、接收、决策、执行和时钟误差。输入观测在锚点之前已变旧的程度另外检查，不能由预测时域代替。TTL、最大观测年龄等阈值通过验证确定。

## 6 带宽与消息大小怎样控制

原始视频留在路侧可显著减少车路链路数据，但多目标多模式轨迹仍需计算开销。以20个目标、6模式、40点、二维float32坐标为例，单次仅坐标为：

20×6×40×2×4 = 38,400字节；10Hz约384,000字节/秒，即3.072Mbit/s。

该值是计算示例，不是实测带宽；尚未包含模式权重、状态、质量、封装、签名、冗余和多接收车开销。Protobuf等二进制封装不能自动消除浮点数组的数据量，实际预算必须对序列化结果计数。若逐车单播，需另算车辆数增长带来的总量；共享广播仅在内容、协议栈与覆盖条件允许时采用。

建议先完成不压缩的正确性基线，再研究目标筛选、采样压缩或量化。目标筛选结合道路冲突关系与可达区域，不能只按距离保留最近几辆。降采样、模式截断和量化均可能改变风险估计，必须对比轨迹误差、危险模式覆盖、预警和闭环碰撞；省略的目标/模式不能默认为安全，消息显式标记覆盖缺口与保留概率质量。

若使用UDP，38KB消息不应直接依赖IP分片传输。可按目标及模式时间块进行应用层分片，每片携带source/session/message_id、目标ID、chunk_index、chunk_count和校验信息，并设重组截止与内存上限；仅完整目标包或协议明确支持的有效部分可用于风险计算。丢片导致的目标不完整必须反馈coverage_complete，不能静默删除危险目标。避免超出路径MTU和控制分片的依据见[RFC 8085第3.2节](https://www.rfc-editor.org/rfc/rfc8085.html#section-3.2)；具体载荷上限按测得MTU、IP/UDP及安全封装开销设置，1200字节只能作为待核查的联调起点。

限速与链路预算一并实现：容量实验可从0.5、1、2、5Mbit/s等人工档位开始；大小为L字节的消息至少占用8L/C秒发送服务时间。同一方向累计排队，带宽不足时按冻结策略淘汰过期项或标记覆盖不足，不能让大量消息在相同时间无成本穿过链路。两个方向共用资源时还需共享调度；独立容量模型是本课题首版简化假设。这些容量档位不代表真实PC5设备规格。

## 7 时延、时钟与失联怎样处理

信息年龄按实际采集时刻计算。车端感知从采集到可用有耗时，V2I有排队与传输，路侧融合/推理有耗时，I2V有排队与传输，车端复核及执行也有耗时。最新路侧观测可能比上传车端观测新，因此融合后仍逐来源、逐目标保留采集时间，不能用单一“消息生成时间”掩盖旧输入。

仿真统一采用CARLA仿真时钟。真实部署需采用适合设备的共同时间基准，如GNSS授时或经校验的时间同步服务，并量化残余偏差；无法跨设备同步时不能仅凭两个本地时间戳声称测得准确单向时延。时钟偏差独立注入实验，不能伪装成负网络延迟。

失联时，车端继续利用本地观测运行CV/Kalman与AEB，侧向避让仍需可观测空间及动力学可行性。已知危险目标短时失联后保留有限风险记忆并扩大不确定性；从未看到的盲区目标不能凭空补出。路口可采取谨慎减速/让行；风险记忆期限和恢复条件另行冻结。

| 丢包/断联/偏钟 | 独立丢包、0.5/1/2秒断联、正负时钟偏差分别施加 | 回退原因可追溯；风险记忆有限；不同异常分别计量 | degradation_events.jsonl |

建议延迟人工档为0、100、200、500ms，丢包档为0%、10%、30%。每次明确这是单向传输延迟还是端到端信息年龄，并记录其余计算与执行延迟。全组合过多时先单因素，再选关键组合交互实验，最后冻结正式测试矩阵。

通信层报告送达率、截止前可用率、数据年龄P50/P95/P99、有效消息字节数、实际吞吐、排队/重组耗时和失联恢复时间。应用层报告完整预测覆盖比例、预警提前量、AEB/AES选择、碰撞率和误干预。丢包率分消息级/分片级，时延统计注明是否包含丢弃包，避免只统计成功消息造成偏差。
