# 开发与 Git 协作规范

更新时间：2026年10月31日。

用户负责研究方向与重要取舍，助手负责后续代码、文档与 Git 管理。此前按用户确认恢复编码前状态后，N01～N10已逐项重新实施并获用户验收；N09已获用户验收；N10几何/覆盖/未知区与原始风险已获用户验收，当前N11单独实施，N12及后续节点仍须单独授权；只有明确授权具体节点后，才创建该节点所需文件、安装依赖或运行任务。逐项执行以 [项目节点实施与验收计划](项目节点实施与验收计划.md) 为统一入口，工程设计、研究方案与技术路线提供技术依据。本约定同时保存在根目录 [AGENTS.md](../AGENTS.md)，供后续开发直接执行。

## 1 工作流程与提交粒度

1. 每次编码、恢复任务或分配编码子任务前，读取AGENTS.md、节点计划总规则、当前节点和前置验收结果，检查分支与工作区；先确认用户只授权了哪个节点。
2. 在当前节点范围内确定一个可独立说明、独立复核的小改动，完成实现和必要检查；不得提前建立后续节点源码、配置、测试或空壳。
3. 复核差异，按具体文件或差异块暂存，再检查暂存内容。
4. 立即中文提交，再做同一节点内的下一项小改动，不积攒大提交。节点必需测试完成后，在计划对应节点回填真实结果、证据与状态并提交。
5. 本节点交付后停止，说明实际验证、效果/限制、证据和提交/推送状态，等待用户验收；不自动进入下一节点。自测通过、用户验收通过、下一节点授权分别记录。

功能、对应测试和必要说明可以组成一个完整提交；无关模块分别提交。不要为凑数量制造无法使用的中间状态。用户已有的无关改动不能混入，也不能擅自删除。当前只维护 Markdown，除非用户另行要求，不生成或同步 Word。

## 2 标准提交结构与中文说明

采用Conventional Commits结构。type必须是标准小写英文；scope、description、body、footer以中文为主，并非强制翻译专有名词、项目标识或标准语法。下文“中文提交”均指这一约定，不再把type翻译成中文。

```text
<type>[(scope)][!]: <description>

[body]

[footer]
```

方括号表示可选，不写入真实提交。type和description必填；scope可省略；`!`仅在真实不兼容变更时使用；没有正文或页脚时直接省略，不留占位文字。标题、正文、页脚之间用空行分隔。

| type | 适用内容 | 格式示例（不代表功能已经实现） |
| --- | --- | --- |
| feat | 新功能 | `feat(通信): 添加消息时效校验` |
| fix | 修补Bug | `fix(风险): 修正延迟预测的时间对齐` |
| docs | 文档修改 | `docs(导航): 补充阅读顺序与资料入口` |
| style | 不影响运行的代码格式调整 | `style(预测): 统一代码缩进` |
| refactor | 不新增功能、不修Bug的代码重构 | `refactor(预测): 拆分编码与模式解码` |
| perf | 性能优化 | `perf(几何): 减少重复坐标转换` |
| test | 增加或修改测试 | `test(通信): 覆盖乱序与过期消息` |
| build | 构建流程或外部依赖变动 | `build(环境): 配置训练依赖组` |
| ci | CI/CD配置或脚本变动 | `ci(检查): 配置文档检查任务` |
| chore | 其他辅助杂项 | `chore(仓库): 忽略系统缓存与本地产物` |
| revert | 回滚已有提交 | `revert(通信): 回滚消息编码变更` |

- **scope**：描述模块或影响范围，可使用“通信”“预测”“文档”等中文；项目模块名如api、web可保留英文。
- **description**：以动作词开头，如“新增、修复、统一、删除”，用现在时动作表述；英文使用add/fix等动词原形，首字母小写，专有名词保留原拼写。末尾不加英文或中文句号，不只写“更新”“修改”“完成”。
- **body**：可选，用中文说明动机、与此前行为的对比、必要实现取舍及真实验证/限制；未运行的检查如实注明，不将计划写成已完成结果。
- **footer**：可选，真实破坏性变更必须用头部`!`或页脚`BREAKING CHANGE: 中文说明`声明，写明不兼容点与迁移要求。真实关联Issue可用`Closes #123`或`Fixes #123`，保留英文标准标识，不编造Issue或破坏性变更。

纯文档内容调整用docs；只改代码空格/分号等才用style，依赖与CI配置分别用build/ci，不把所有辅助变更都记成chore。一个提交只表达一个可独立复核的改动，继续按步骤、按模块小步提交。

## 3 分支与推送

优先使用适合当前任务的已有工作区与分支；新建开发分支使用 `binfinity/` 前缀。不默认要求额外 PR，也不为每个小提交新建分支。

跨电脑开发前必须获取并核对远端最新状态，检查当前分支、上游、工作区和暂存区；仅工作区安全且能快进时同步。远端不可达或分支分叉时保留现场并说明，不把本地旧跟踪引用称为最新，不擅自覆盖或清理改动。换电脑前完成小步提交并按已有推送授权同步；下次在另一台重新检查。完整操作顺序及移动硬盘约定见 [跨电脑开发与移动硬盘约定](跨电脑开发与移动硬盘约定.md)。

推送前核对远程地址、分支和待推送提交，检查远程是否有新增改动。用户已经授权推送时，检查后直接推送；推送后核对本地与远程提交一致。尚未授权推送的任务保留本地提交，并在交付中说明。

未经明确授权，不强制推送、不改写已发布历史、不删除远程分支、不清理用户未提交内容。发生冲突先核对双方改动，不能以覆盖未知远程内容解决冲突。

用户明确要求修订旧提交信息时，先核对分支、标签、引用和签名。仅修message须保留每个提交的文件树、作者/提交者时间和顺序；带签名的提交不能原样保留有效签名又修改消息，默认保留。已推送历史只有在本次明确授权覆盖该范围时才修订，并用绑定已核对远程提交的`--force-with-lease`推送；远程变化或保护规则拒绝时停止覆盖，不退回无条件强推。本规则不是日常节点任务自动获得的历史改写权限。

## 4 文档与历史

各文件职责见 [文档导航](README.md)。涉及课题方案、实现、实验或论文的实质更新，同步维护 [研究方案](毕业设计研究方案.md) 中的当前结论；涉及算法、接口或参数时同步维护 [详细技术路线](详细技术路线.md) 及专题文档。

文档与代码版本及变更说明统一由中文 Git 提交管理，不再维护独立更新记录、历史记录或CHANGELOG文档，不建立 `history` 目录，也不在每次修改前复制快照或备份。查看旧版使用 `git log -- 路径` 和 `git show 提交:路径`，需要恢复时从对应提交提取。核查证据保留其实际时间与范围；普通静态检查默认输出终端，不为每次检查积累报告副本。保留 `thesis/` 论文目录与已有 SVG。

用户要求的节点计划负责保存每项实施约定、当前状态与真实验收摘要，同一文件对应节点持续回填；这是后续执行入口，不恢复通用历史日志。原始run、权重和视频保存在产物目录，计划只登记路径、哈希与复核方法。

## 5 实现与证据

结论分别标注为建议、待验证假设、论文报告结果、本项目实际运行结果或已复核结果。新增模块写清输入、输出、算法步骤、代码入口、参数、测试输入、期望断言和保存产物。

拟建目录、命令和接口须标为拟建，实际创建并验证后再改变状态。文档核查、参考函数运行、训练实验和 CARLA 闭环分别记录，不能用语法检查代替系统验证，不编造指标、实验数量或改进幅度。

风险标签须包含未来时域与参考策略，区分实际碰撞、近冲突代理和仿真反事实。闭环控制只能读取决策时刻已可用的历史观测，不能读取不可见目标真值或未来数据。

节点必需测试失败、跳过或未执行时不能记通过。门槛需要调整时，先说明原因、范围与影响并取得用户确认，不能为通过而降标；共享模块变动补受影响的已完成节点回归。代码完成并提交后，用不可变的被测代码提交/源码哈希回填证据，避免仅引用HEAD或文档自身哈希。用户未明确验收时保持“未验收”。

### 训练与开发图表留存

训练与开发过程中必须保留可复核的指标记录和图表：训练默认每次优化更新记录原始指标（step、epoch、样本分母、loss及分项、训练误差、梯度、学习率、耗时和资源），按epoch单独记录验证指标；自动保存PNG/SVG、原始CSV/JSON和图表来源/哈希。失败、中断及恢复记录保留，图表不能替代原始记录，不伪造逐步验证指标，不以平滑曲线替代原值。开发/评测按当前节点保存适用的诊断图、失败样例或指标表；不适用须注明。图片保存约定（2026-10-31用户明确要求）：训练、评测和开发生成的全部过程图片必须存入项目`docs/过程图/`，使用中文文件名，按节点/运行ID/seed区分，保留PNG/SVG原件、失败样例及来源/哈希，并随Git提交、按授权推送。不得仅将图片留在移动硬盘；已有入口先写硬盘时，交付前运行`scripts/archive_process_images.py`完成中文归档并复核。原始数据、CSV/JSON、大型日志、权重、视频仍放移动硬盘，不入普通Git。旧图片地址通过迁移映射追溯，不改写历史不可变被测版本或指标。

## 6 仓库收录范围

普通 Git 收录代码、公开配置模板、文档、必要图源、小型示例和核查记录。原始大数据、模型权重、大规模日志与视频保存在外部或本地被忽略的产物目录，并通过数据版本、配置、清单和哈希关联。系统缓存、虚拟环境和凭据不提交。

`.gitignore` 中的 `/data/`、`/artifacts/` 等规则针对未来本地产物，不表示这些目录已经存在。`docs/figures/` 与 `docs/validation/` 中的现有交付资料继续纳入版本管理。

N11当前仅实现解析模式下的S曲线、TTC/原始风险AEB与12分支配对；输入、算法、参数、测试和停止边界见[N11协议](N11解析制动与因果闭环协议.md)。未执行CARLA/视频、AES/MPC或真实制动标定；结果统一回填节点计划。过程图中文归档并随Git保存。
