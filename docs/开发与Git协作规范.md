# 开发与 Git 协作规范

更新时间：2026年10月26日。

用户负责研究方向与重要取舍，助手负责后续代码、文档与 Git 管理。当前工作以文档整理为主，算法实现以研究方案和详细技术路线为依据。本约定同时保存在根目录 [AGENTS.md](../AGENTS.md)，供后续开发直接执行。

## 1 工作流程与提交粒度

1. 开始前读协作约定，检查当前分支、工作区差异和相关文档。
2. 确定一个可独立说明、独立复核的小改动，完成实现和必要检查。
3. 复核差异，按具体文件或差异块暂存，再检查暂存内容。
4. 立即提交，然后进入下一步骤或模块。不要等整项任务结束才一次性提交。
5. 交付时说明改动、实际验证、剩余事项、提交与推送状态。

功能、对应测试和必要说明可以组成一个完整提交；无关模块分别提交。不要为凑数量制造无法使用的中间状态。用户已有的无关改动不能混入，也不能擅自删除。当前只维护 Markdown，除非用户另行要求，不生成或同步 Word。

## 2 中文提交格式

统一采用 `类型(范围): 中文动作与结果`。类型、范围、标题与正文使用中文，技术名称和标识符保留原文。

| 类型 | 适用内容 | 示例 |
| --- | --- | --- |
| 文档 | 方案、导航、图集说明 | `文档(导航): 补充阅读顺序与资料入口` |
| 功能 | 新增可用能力 | `功能(通信): 实现消息时效检查` |
| 修复 | 修正行为或内容错误 | `修复(风险): 修正延迟预测的时间对齐` |
| 重构 | 保持行为的结构调整 | `重构(预测): 拆分编码与模式解码` |
| 测试 | 新增或修订有效验证 | `测试(通信): 覆盖乱序与过期消息` |
| 构建 | 依赖和构建配置 | `构建(环境): 增加开发依赖配置` |
| 维护 | 仓库日常管理 | `维护(仓库): 忽略系统缓存与本地产物` |

避免仅写“更新”“修改”“完成”。涉及取舍或复杂逻辑时，用提交正文写清原因、主要变化、实际检查与限制；未运行的检查必须如实注明。

## 3 分支与推送

优先使用适合当前任务的已有工作区与分支；新建开发分支使用 `binfinity/` 前缀。不默认要求额外 PR，也不为每个小提交新建分支。

推送前核对远程地址、分支和待推送提交，检查远程是否有新增改动。用户已经授权推送时，检查后直接推送；推送后核对本地与远程提交一致。尚未授权推送的任务保留本地提交，并在交付中说明。

未经明确授权，不强制推送、不改写已发布历史、不删除远程分支、不清理用户未提交内容。发生冲突先核对双方改动，不能以覆盖未知远程内容解决冲突。

## 4 文档与历史

各文件职责见 [文档导航](README.md)。涉及课题方案、实现、实验或论文的实质更新，同步维护 [研究方案](毕业设计研究方案.md) 与 [更新记录](更新记录.md)；涉及算法、接口或参数时同步维护 [详细技术路线](详细技术路线.md) 及专题文档。

文档与代码版本统一由 Git 管理，不再维护 `history` 目录，也不在每次修改前复制快照或备份。查看旧版使用 `git log -- 路径` 和 `git show 提交:路径`，需要恢复时从对应提交提取。核查证据保留其实际时间与范围；普通静态检查默认输出终端，不为每次检查积累报告副本。保留 `thesis/` 论文目录与已有 SVG。

## 5 实现与证据

结论分别标注为建议、待验证假设、论文报告结果、本项目实际运行结果或已复核结果。新增模块写清输入、输出、算法步骤、代码入口、参数、测试输入、期望断言和保存产物。

拟建目录、命令和接口须标为拟建，实际创建并验证后再改变状态。文档核查、参考函数运行、训练实验和 CARLA 闭环分别记录，不能用语法检查代替系统验证，不编造指标、实验数量或改进幅度。

风险标签须包含未来时域与参考策略，区分实际碰撞、近冲突代理和仿真反事实。闭环控制只能读取决策时刻已可用的历史观测，不能读取不可见目标真值或未来数据。

## 6 仓库收录范围

普通 Git 收录代码、公开配置模板、文档、必要图源、小型示例和核查记录。原始大数据、模型权重、大规模日志与视频保存在外部或本地被忽略的产物目录，并通过数据版本、配置、清单和哈希关联。系统缓存、虚拟环境和凭据不提交。

`.gitignore` 中的 `/data/`、`/artifacts/` 等规则针对未来本地产物，不表示这些目录已经存在。`docs/figures/` 与 `docs/validation/` 中的现有交付资料继续纳入版本管理。
