# N12 仿真桥接与时钟协议

范围为本机独立算法进程与 CARLA 的同步通信、观测过滤和评测旁路；实施与实际验收状态以[节点计划](项目节点实施与验收计划.md#n12-carla桥接同步时钟与真值隔离)为准。用户选择 CARLA 0.9.16，核心与桥接均使用 Python 3.11；选择版本不等于已完成本机客户端与服务端握手。

核心 `scripts/run_carla_bridge.py` 可在 IDE 无必填参数运行；默认本机 127.0.0.1:2000、0.05 s、200 帧、RGB 等待 0.5 s、桥接解释器和产物写入本机 H 盘项目目录。更换电脑时通过可选命令行参数覆盖实际解释器、硬盘目录、地址和端口；路径不依赖启动目录。脚本不下载或启动服务端，缺依赖、连接失败或版本不符必须报错。该入口仅输出安全复核后的静止制动，用于同步实验，不能作为执行器标定或实际避撞效果。

桥接运行于独立 Python 环境，核心不安装或导入 CARLA。双方以本机认证 IPC 传输长度受限的 JSON；核心发 N02 `AdvanceRequest`，runner 按运行、episode、generation、时钟、下一帧、有效期校验并单独持有 World 和推进 tick。桥接返回 N02 `TickEvent` 与按帧白名单校验的 RGB；缺帧有界等待后明确标记 invalid，不使用未来帧补当前帧。同步配置为固定步长 0.05 s、物理子步上限 10、最大子步 0.01 s，完成或异常时尝试只销毁本次 actor 并恢复原设置。若服务端已断开导致无法清理或恢复，必须记录实际失败，不宣称恢复成功。

桥接侧 `truth_logger` 将本次自车位姿写入评测旁路，不通过 IPC 发给在线核心；这不等于已实现完整多目标真值、感知或场景闭环。进程内真实 IPC 模拟服务端夹具只检验通信与隔离机制，不替代实际 CARLA 结果。独立 `scripts/test_n12_carla_cleanup.py` 须用桥接 Python 运行，针对断连、超时和异常注入，旁路对比服务设置及 actor 集合；实际能否通过须以运行报告为准。

每次运行输出配置、握手、逐帧 JSONL、异常请求、桥接日志及评测真值。成功完成时按原始逐帧数据生成中文文件名图表与来源哈希；所有运行产物和过程图保留在移动硬盘，不纳入普通 Git。前期失败、中断日志也保留。已取得真实服务端 200 个连续 tick 和 IPC 断连等故障清理证据；失联原生崩溃已修复，停服后原世界的清理与恢复仍未完成，本节点自测未通过，详见节点计划。

2026-10-31 失联排查已定位一个项目代码触发点：新生成的手动车辆调用了 `set_autopilot(False)`。CARLA 0.9.16 的 [Vehicle::SetAutopilot](https://github.com/carla-simulator/carla/blob/0.9.16/LibCarla/source/carla/client/Vehicle.cpp) 会无条件获取或创建 Traffic Manager；[TrafficManagerLocal](https://github.com/carla-simulator/carla/blob/0.9.16/LibCarla/source/carla/trafficmanager/TrafficManagerLocal.cpp) 的后台线程会读取世界设置。服务端失联可使这类 RPC 失败。Windows 原始事件显示 `ucrtbase.dll`、异常 `0xC0000409` 和子码 7；[Microsoft 对 fast fail 的说明](https://learn.microsoft.com/en-us/cpp/intrinsics/fastfail?view=msvc-170)明确其绕过异常处理器，不能指望 Python 的 `try/finally` 接住。该异常码本身不能证明内存越界。本次没有原生调用栈，因此“后台 RPC 异常触发 C++ 终止”属于源码与事件支持的路径推断，不断言具体抛出行。

独立真实 A/B 试验中，除了这一调用外使用相同车辆生成与服务中断步骤，不含核心 IPC 或请求超时注入：调用关闭自动驾驶的2次均以 `0xC0000409` 退出；保持默认手动控制的2次均捕获到 Python RPC 异常并正常结束诊断程序。该触发条件已在本机复现。runner 已删除多余调用，未使用 Traffic Manager。`scripts/diagnose_n12_server_loss.py` 可在 IDE 默认执行两组各2次试验；有现存服务监听2000端口时拒绝执行，只中断本入口创建的服务进程树。`--bridge-only` 单独验证完整桥接的服务端中断路径；失败结果须阅读原始报告，入口正常结束只表示试验已执行，不表示 N12 验收通过。

桥接现在以5 s RPC期限处理正常运行阶段的请求；初始化握手保留15 s期限。`probe_server` 仅查询版本，不读取目标或推进世界，独立失联试验不再混用请求超时。`清理报告.json` 逐项记录本次 actor 的销毁确认、原始异常、设置恢复和清理错误，`进程退出.json` 保存退出码和十六进制值。完整桥接实测由原生快速终止变为 Python 退出码1，报告明确 `status=failed`、两只本次actor销毁未获确认、`settings_restored=false`。服务端已终止时原世界不存在，离线RPC不能恢复该世界；本次没有实现或宣称重建原世界、自动重启服务或透明重连，原验收标准未修改。

最新实际结果、不可变版本和证据路径统一回填节点计划。正常200帧及IPC断连/超时/异常三项真实清理回归通过；服务端彻底停止的恢复项继续失败，N13未授权。

用户已于2026-10-31明确同意第⑤项按服务可恢复/不可恢复区分，授权补齐短暂失联安全收尾。实现参数预先确定：恢复预算12 s、单RPC期限0.5 s、重试间隔0.25 s，清理实测上限15 s；只在世界ID和本运行对象归属均匹配时恢复设置并清理，不恢复旧请求执行。失败和早期原生崩溃证据保留。
