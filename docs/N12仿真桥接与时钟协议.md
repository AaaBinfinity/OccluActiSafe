# N12 仿真桥接与时钟协议

范围为本机独立算法进程与 CARLA 的同步通信、观测过滤和评测旁路；实施与实际验收状态以[节点计划](项目节点实施与验收计划.md#n12-carla桥接同步时钟与真值隔离)为准。用户选择 CARLA 0.9.16，核心与桥接均使用 Python 3.11；本机客户端与服务端已实际握手且版本均为0.9.16。

核心 `scripts/run_carla_bridge.py` 可在 IDE 无必填参数运行；默认本机 127.0.0.1:2000、0.05 s、200 帧、RGB 等待 0.5 s、桥接解释器和产物写入本机 H 盘项目目录。更换电脑时通过可选命令行参数覆盖实际解释器、硬盘目录、地址和端口；路径不依赖启动目录。脚本不下载或启动服务端，缺依赖、连接失败或版本不符必须报错。该入口仅输出安全复核后的静止制动，用于同步实验，不能作为执行器标定或实际避撞效果。

桥接运行于独立 Python 环境，核心不安装或导入 CARLA。双方以本机认证 IPC 传输长度受限的 JSON；核心发 N02 `AdvanceRequest`，runner 按运行、episode、generation、时钟、下一帧、有效期校验并单独持有 World 和推进 tick。桥接返回 N02 `TickEvent` 与按帧白名单校验的 RGB；缺帧有界等待后明确标记 invalid，不使用未来帧补当前帧。同步配置为固定步长 0.05 s、物理子步上限 10、最大子步 0.01 s，完成或异常时尝试只销毁本次 actor 并恢复原设置。短暂失联只允许在世界ID和运行归属一致时完成清理；不可恢复或身份不匹配时限时结束并记录失败，不宣称恢复成功。

桥接侧 `truth_logger` 将本次自车位姿写入评测旁路，不通过 IPC 发给在线核心；这不等于已实现完整多目标真值、感知或场景闭环。进程内真实 IPC 模拟服务端夹具只检验通信与隔离机制，不替代实际 CARLA 结果。独立 `scripts/test_n12_carla_cleanup.py` 须用桥接 Python 运行，针对断连、超时和异常注入，旁路对比服务设置及 actor 集合；实际能否通过须以运行报告为准。

每次运行输出配置、握手、逐帧 JSONL、异常请求、桥接日志及评测真值。成功完成时按原始逐帧数据生成中文文件名图表与来源哈希；所有运行产物和过程图保留在移动硬盘，不纳入普通 Git。前期失败、中断日志也保留。已取得真实服务端 200 个连续 tick 和 IPC 断连等故障清理证据；按用户确认的新第⑤项，短暂失联同世界收尾、不可恢复限时失败均已实测通过；当前待用户验收，详见节点计划。

2026-10-31 失联排查已定位一个项目代码触发点：新生成的手动车辆调用了 `set_autopilot(False)`。CARLA 0.9.16 的 [Vehicle::SetAutopilot](https://github.com/carla-simulator/carla/blob/0.9.16/LibCarla/source/carla/client/Vehicle.cpp) 会无条件获取或创建 Traffic Manager；[TrafficManagerLocal](https://github.com/carla-simulator/carla/blob/0.9.16/LibCarla/source/carla/trafficmanager/TrafficManagerLocal.cpp) 的后台线程会读取世界设置。服务端失联可使这类 RPC 失败。Windows 原始事件显示 `ucrtbase.dll`、异常 `0xC0000409` 和子码 7；[Microsoft 对 fast fail 的说明](https://learn.microsoft.com/en-us/cpp/intrinsics/fastfail?view=msvc-170)明确其绕过异常处理器，不能指望 Python 的 `try/finally` 接住。该异常码本身不能证明内存越界。本次没有原生调用栈，因此“后台 RPC 异常触发 C++ 终止”属于源码与事件支持的路径推断，不断言具体抛出行。

独立真实 A/B 试验中，除了这一调用外使用相同车辆生成与服务中断步骤，不含核心 IPC 或请求超时注入：调用关闭自动驾驶的2次均以 `0xC0000409` 退出；保持默认手动控制的2次均捕获到 Python RPC 异常并正常结束诊断程序。该触发条件已在本机复现。runner 已删除多余调用，未使用 Traffic Manager。`scripts/diagnose_n12_server_loss.py` 可在 IDE 默认执行两组各2次试验；有现存服务监听2000端口时拒绝执行，只中断本入口创建的服务进程树。`--bridge-only` 单独验证完整桥接的服务端中断路径；失败结果须阅读原始报告，入口正常结束只表示试验已执行，不表示 N12 验收通过。

桥接现在以5 s RPC期限处理正常运行阶段的请求；初始化握手保留15 s期限。`probe_server` 仅查询版本，不读取目标或推进世界，独立失联试验不再混用请求超时。`清理报告.json` 逐项记录本次 actor 的销毁确认、原始异常、设置恢复和清理错误，`进程退出.json` 保存退出码和十六进制值。完整桥接实测由原生快速终止变为 Python 退出码1，报告明确 `status=failed`、两只本次actor销毁未获确认、`settings_restored=false`。服务端已终止时原世界不存在，离线RPC不能恢复该世界；这份报告属于之前标准下的实测，不追溯改写。用户随后明确修订第⑤项，现已补齐有限收尾重连；不重建世界、自动重启服务或续跑旧请求。

最新实际结果、不可变版本和证据路径统一回填节点计划。按用户修订的第⑤项，正常200帧、IPC断连/超时/异常、短暂RPC失联及永久中断/服务端终止的限时失败均通过。运行本身在故障注入时仍标失败，与验收检查正确通过分开。N13未授权。

用户已于2026-10-31明确同意第⑤项按服务可恢复/不可恢复区分，授权补齐短暂失联安全收尾。实现参数预先确定：恢复预算12 s、单RPC期限0.5 s、重试间隔0.25 s，清理实测上限15 s；只在世界ID和本运行对象归属均匹配时恢复设置并清理，不恢复旧请求执行。失败和早期原生崩溃证据保留。


本轮实现由 `SynchronousRunner.close()` 持锁关闭推进接口，再按12 s预算执行清理；healthy状态复用原客户端，RPC失败才创建新连接。先用真实settings RPC核对当前CARLA世界ID，再核对全部本次actor的编号、type与 `role_name=oas:<run_id>`；全部预检通过后才按编号销毁、恢复原设置并复核。创建车辆时必须保留已设置标记的蓝图实例，避免重新索引蓝图库取得未修改副本。世界更换或归属不符直接拒绝修改；历史重试错误保留，清理成功也不续跑当前episode。清理报告通过临时文件原子替换保存；报告盘写入失败不能阻止actor清理，但仍以证据失败退出。

`reconnect`、`destroy_command`、`prepare_cleanup` 等构造参数均为可选扩展，原有runner调用及N02消息格式不变。本轮未改已验收核心算法或公共数据契约，已补N02回归。后续仍可使用桥接；恢复路径只终结当前运行，重新开始必须用新run及generation上下文。

真实验收入口为 `scripts/test_n12_recovery.py`：默认拒绝接管现存服务，启动本次专用CARLA，用独立桥接环境的旁路观察者检查原设置和外部验证车辆。TCP代理会关闭已有RPC连接并短暂或永久拒绝新连接，不伪造服务端响应、不修改系统防火墙；另真实终止本次服务端测试不可恢复路径。输出原始7类检查JSON、代理中断事件、日志、每个run的清理/进程退出报告和中文PNG/SVG；检查正常结束代表断言通过，不代表故障episode成功。永久隔离实验的残留由测试旁路在验收证据保存后核对归属、定向清理，此测试收尾单独留证。

实际断言包括：真实200个连续tick与三个非法请求拒绝；短暂失联时无额外tick、恢复后同世界/原设置/原有23个actor及外部验证车辆保留；永久隔离及服务终止时清理不超过15 s、故障到进程退出不超过25 s、退出码1且明确未恢复设置；世界更换、编号复用但归属不同和证据盘故障另由机制夹具验证。最新不可变代码、全部分母和限制均见节点计划。
